最近听到这么一种说法：在 AI 检索中，grep 比 RAG 更好。

乍一听，这像是在抬杠。RAG 过去几年一直被视为让模型用上外部知识的正路，而 grep 只是一个再古老不过的文本搜索命令。

但把视线移到 AI 编程 Agent 的真实工作过程，就会发现这个说法并非空穴来风。

一边是过去几年被反复讲述的故事：把代码切块、向量化、存进向量数据库，提问时做语义检索，再把相关片段塞给模型。这就是很多人理解的 RAG。

另一边是终端里真实发生的操作：`rg -n "ECONNREFUSED"`、`rg -l "useEffect"`、`git grep "TODO"`。没有 embedding，没有向量库，甚至没有索引。

一个代表「语义相似」，一个代表「精确命中」。它们迎头撞上时，为什么赢的经常是后者？

这个说法值得认真讨论，但不能照字面理解。grep 是一个检索工具，RAG 是一套「检索增强生成」的流程；grep 完全可以成为 RAG 里的一个 retriever。真正要比较的，是两种思路：

- **精确检索 + 让 Agent 反复搜索、阅读、验证**
- **向量检索 + 一次性取回 top-k 片段塞进上下文**

在代码这个场景里，前者经常赢。原因不是 grep 更「先进」，而是代码这种材料的性质，恰好站在精确检索那一边。

## 一、先把概念摆正：grep 和 RAG 不在同一个层级

先把两者放在同一张表里看：

| | grep / ripgrep | 常见的向量 RAG |
| --- | --- | --- |
| 输入 | 字面量、正则、glob | 自然语言问题 |
| 检索单位 | 文件、行 | 切块后的 chunk |
| 排序依据 | 是否匹配 | 向量相似度 |
| 返回内容 | 文件路径 + 行号 + 原文 | top-k 片段 + 相似度分数 |
| 索引 | 通常不需要 | 需要 embedding 索引 |
| 可验证性 | 高：能直接回到原文 | 中：相似不等于正确 |

需要说明的是，**RAG 不等于向量数据库**。BM25、SQL、grep 都可以是 RAG 的检索器。本文说的 RAG，特指最常见的做法：把文档切成 chunk，用 embedding 做稠密向量检索，再取 top-k 拼进上下文。

所以「grep 比 RAG 更好」更准确的说法是：

> 在代码库里，**精确检索 + 迭代搜索**往往比**向量相似度 + 一次性注入**更可靠。

## 二、代码里的问题，往往是「字面量问题」

程序员找代码时，脑子里想的经常不是一段语义，而是一个具体字符串：

- 报错信息：`ECONNREFUSED 127.0.0.1:5432`
- 环境变量：`DATABASE_URL`
- 接口路径：`/api/v1/login`
- 配置项：`maxRetries`
- 函数名：`getUserById`
- 日志里的 trace id、错误码、feature flag

这些查询的共同点是：**答案必须精确匹配，差一个字符都不行。**

向量检索擅长「意思差不多」，但代码里「意思差不多」常常意味着「不是这个」。`getUserById` 和 `getUserByID` 在语义上几乎一样，在编译器眼里却是两个符号；`timeout` 和 `timeOut` 也可能是两个配置项。

| 你要找的 | grep | 向量检索 |
| --- | --- | --- |
| `ECONNREFUSED` | 直接命中配置或日志 | 可能返回「数据库连接失败」的泛泛段落 |
| `useEffect` 的调用点 | 精确列出文件和行 | 可能把 `useLayoutEffect` 也排进来 |
| `X-Auth-Token` | 精确命中请求头 | 可能召回「鉴权」相关但错误的代码 |

这并不是说 embedding 处理不了代码。代码模型也能学到标识符和结构，但对于一大类代码查询，精确匹配同时更便宜、更可靠，也更容易解释。

## 三、代码的正确性，靠的是位置和引用

代码不是散文。一个函数的意义，来自它在哪里定义、被谁调用、依赖什么类型、被哪些测试覆盖。RAG 把代码切成 chunk，天然会切断这些关系：

- 函数签名和函数体被切开；
- import 和实际使用被切开；
- 类型定义、实现、调用点分散在不同 chunk；
- 注释和它解释的那行代码分开。

然后向量检索按「这段文字像不像问题」来排序。它可以找到「看起来相关」的段落，却不一定找到「真正影响这次修改」的位置。

grep 返回的是 `path:line`。这个信息很朴素，但它让 Agent 能继续往下走：打开文件、看上下文、找调用点、读测试。检索不是终点，而是定位的起点。

> 向量检索回答的是「哪段文字最像」，grep 回答的是「这个东西在哪里」。在代码里，后者通常更有用。

## 四、代码库是活的，索引不是

向量索引最怕的不是建不起来，而是建起来之后没人敢信。

一个正在开发的项目，随时可能出现这些变化：

- 刚改过但还没提交的文件；
- 切换分支后完全不同的一套代码；
- 构建生成的产物、临时文件、被 gitignore 的本地配置；
- monorepo 里频繁变动的子包；
- 新增的依赖和自动生成的类型。

grep 每次读的都是当前磁盘上的内容，天然不会过期。向量索引则要考虑增量更新、删除同步、分支隔离、权限过滤，以及「索引里到底有没有包含我刚刚写的那一行」。

这不是说索引一定做不好，而是说它引入了一整类新的维护问题。对个人项目和小团队来说，**没有索引，很多时候就是最好的索引**。

## 五、Agent 把检索从「一次性管道」变成了「循环」

这是我认为最关键的一点。

经典 RAG 的流程是线性的：

```text
用户问题 → 检索 top-k → 拼接上下文 → 模型回答
```

它假设你在提问的那一刻，就已经能把问题描述清楚，并且一次检索就能召回足够的信息。

但真实的调试过程不是这样。比如「登录偶尔失败」这个模糊的问题，人通常会这样查：

1. `rg -n "login failed|invalid session" src`，先找错误信息；
2. 打开命中的 session 中间件，发现 token 有一个过期时间；
3. `rg -n "SESSION_TTL|maxAge" .`，追到配置；
4. 读相关测试，发现测试里用了伪造时钟；
5. 再回到代码，确认边界条件。

每一步的搜索结果，都会改变下一步要搜什么。词汇是在读代码的过程中逐渐长出来的，而不是提问前就想好的。

Agent 把这个过程变成了可执行的循环：

```text
问题 → grep → 读文件 → 形成假设 → 再 grep → 读测试 → 验证 → 回答或修改
```

单次 grep 很便宜，所以 Agent 可以失败很多次。查不到就换关键词，结果太多就加 glob，命中太少就放宽正则。相比之下，RAG 的一次 top-k 更像「一锤子买卖」：召回错了，模型只能在错误的上下文里继续推理。

> RAG 假设你能在提问时把问题描述清楚；Agent 搜索允许你在读代码的过程中，逐步把问题描述清楚。

## 六、成本账：不只算 token

RAG 的成本经常被低估。它不只是「调用一次 embedding API」：

- 要选 embedding 模型，还要跟随模型升级重建索引；
- 要决定 chunk 大小、重叠长度和切分方式；
- 要维护向量库、元数据和增量更新；
- 要做权限过滤，避免把不该看的内容召回；
- 要调 top-k、相似度阈值和 rerank 策略；
- 要评估检索质量，而不仅是最终回答看起来对不对。

grep 的成本主要花在「搜索策略」上：关键词怎么选、范围怎么限定、结果怎么读。它不需要额外服务，不依赖网络，通常在本地几秒内就能跑完。

当然，grep 也不是没有代价。搜索范围太大时，输出会非常吵；一个常见词可能命中几千行。所以真正有效的用法不是「无脑 grep」，而是带着约束去搜：限定目录、文件类型、单词边界和上下文行数。

## 七、但 grep 不是万能的：RAG 仍然赢的场景

如果文章停在这里，就容易变成「向量检索一无是处」的情绪输出。事实上，RAG 在另一类问题上明显更强。

### 1. 自然语言知识库

设计文档、RFC、会议记录、工单、聊天历史、PDF 手册，这些内容本来就用自然语言写成。用户的问题也往往是模糊的：

> 「我们之前为什么决定不用消息队列？」

这种问题没有唯一的字面量锚点，语义检索更合适。

### 2. 你不知道代码里的词汇

假设你想找「哪里处理了限流」，但代码里用的是 `token bucket`、`throttle` 或 `rate limiter`。如果你一个词都猜不到，grep 就会空手而归；语义检索可以从概念层面把相关代码捞出来。

### 3. 精确词太常见，需要排序

搜索 `timeout` 可能命中几千处。这时需要的不是「是否匹配」，而是「哪几处最相关」。全文排序（BM25）或向量 rerank 就派上用场了。

### 4. 跨语言、同义词和改写

同一个概念可能以中文注释、英文变量名、缩写和业务黑话同时存在。语义检索在词汇不统一时更有优势。

### 5. 非文本或多模态内容

图片、音频、扫描件、演示文稿，grep 天然无能为力。这类内容需要另一套检索方式。

| 任务 | 更合适的选择 |
| --- | --- |
| 找某个函数的所有调用点 | grep + LSP |
| 查报错信息对应的配置 | grep |
| 在大量文档里找相关设计 | 向量检索 / BM25 |
| 不知道关键词，只知道大概意思 | 语义检索 |
| 确认某行代码是否真的执行 | 读代码 + 运行测试 |
| 在图片或 PDF 里找信息 | 多模态检索 |

## 八、更好的答案：检索阶梯，而不是站队

与其争论「grep 还是 RAG」，不如把检索看成一个阶梯。每次先用最便宜、最可验证的那一级，不够再往上走：

1. **精确字符串 / 正则**：`rg`、`git grep`，用于标识符、报错、配置项；
2. **符号与引用**：LSP、ctags，用于定义、跳转、找引用；
3. **全文排序**：BM25，用于关键词太常见、需要排序的场景；
4. **向量 / 语义检索**：用于自然语言问题、词汇不统一、跨文档召回；
5. **问人 / 读文档**：用于前四级都无法消化的模糊问题。

对 AI 编程 Agent 来说，一个实用的默认组合是：

- 代码定位：优先 `ripgrep`；
- 定义与引用：接 LSP 或语言服务器；
- 文档与历史讨论：语义检索；
- 最终判断：读原文、跑测试、看 diff。

这不是「grep 打败了 RAG」，而是「检索终于回到了它该在的位置」：**检索是为了获得下一步可验证的信息，而不是为了把上下文塞满。**

## 九、几个可直接用的 grep 习惯

最后放几个日常写代码和用 Agent 时都实用的习惯：

```bash
# 精确查找标识符，避免匹配到更长的单词
rg -n -w 'getUserById' src

# 查找报错信息，并带 3 行上下文
rg -n -C 3 'ECONNREFUSED|connection refused' .

# 限定文件类型，排除依赖目录
rg -n -g '*.ts' -g '!node_modules' 'TODO|FIXME' .

# 只列出命中的文件，先看范围
rg -l 'useEffect' src

# 搜索隐藏文件（-u 可以进一步包含被 .gitignore 忽略的文件）
rg -n --hidden -g '!.git' 'apiKey' .

# 把模式当成固定字符串，避免正则元字符干扰
rg -n -F 'user.name' .
```

几个小建议：

- 搜不到时，先换同义词、缩写和更短的片段，不要急着认定「代码里没有」；
- 搜到太多时，加 `-g` 限定目录或文件类型，而不是直接翻几千行；
- 别只搜 `src`，配置、测试、脚本和文档里经常藏着答案；
- 找到定义之后，继续找调用点和测试，才算真正定位。

## 十、结论：grep 赢的不是搜索，而是可验证的迭代

「grep 比 RAG 更好」这句话，在代码场景下有一半是真的。

grep 的优势是精确、实时、便宜、可验证，而且非常适合 Agent 反复试错。RAG 的优势是模糊召回、自然语言理解、跨文档泛化和语义相似。它们解决的不是同一个问题，也不应该被迫二选一。

真正值得记住的是：

> **在代码里，最好的检索不是一次漂亮的相似度排序，而是一条能走到底、并且每一步都能验证的线索。**

所以，与其问「grep 还是 RAG」，不如问：

**我需要的是一次「看起来相关」的召回，还是一条「可以继续查下去」的路径？**

对大多数代码任务，答案往往是后者。也正因为如此，grep 才会在 AI 编程工具里反复出现——它不是复古，而是回到了检索最朴素、也最可靠的样子。
