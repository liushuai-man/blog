假设某天工作群里多了一条消息：“这个功能再做个微信小程序吧，应该跟网页差不多。”

如果之前一直写 Web，第一反应多半是：用 Vue 还是 React？页面能不能直接搬？开发者工具又是什么？

先别急着建项目。页面之外，账号权限、登录方式、真机差异、备案和版本审核，都是排期里容易漏掉的工作。

下面拿 `exai-miniprogram` 做案例。它是一个账户类小程序，包含钱包、卡册、兑换、转赠和资料编辑。**目前是可交互的前端演示，正式登录、验证码、支付和资产归属仍待后端接入。** 本文以微信为主，也会说明和支付宝小程序的共通点。

## 第一天，先把“能不能做”问清楚

我会先确认四件事：

- **做给谁，第一版做到哪里？** 先列出必须走通的用户流程，例如登录、查看账户、兑换、查看结果。别用“十个页面”代替需求边界。
- **谁提供平台账号？** 小程序归哪个主体，AppID 是否已有，谁是管理员，开发者和体验者权限由谁添加。
- **需要哪些平台能力？** 登录、手机号、分享、支付分别核对，同时确认服务类目、资质、备案和隐私声明的要求。
- **后端准备到哪了？** 有没有测试环境、HTTPS 域名、接口契约，以及账户和订单的负责人。

账号和材料准备可以与开发并行。尤其是充值、兑换这类功能，要尽早确认业务规则和平台是否支持预期的实现方式。

## 小程序，究竟运行在哪里

网页由浏览器打开 URL，加载 HTML、CSS 和 JavaScript。小程序则把代码和资源组织成平台识别的包，由微信、支付宝这样的**宿主 App**加载和运行；业务数据仍可以请求自己的服务器。

宿主提供页面管理、组件和设备能力，开发者通过平台 API 调用。例如微信用 `wx.request` 发请求、`wx.navigateTo` 打开页面，支付宝则有自己的 `my.*` API。

以微信原生框架为例，WXML 描述页面结构，WXSS 写样式，JavaScript 处理逻辑，JSON 配置页面和组件。它们看起来很像 Web，但运行方式有区别：视图层和逻辑层分开，点击事件传给逻辑层，再通过 `setData` 同步展示数据。

**点按钮 → 执行业务逻辑 → 更新视图数据 → 界面变化。**

因此不能照搬 `document.querySelector` 等 DOM 操作，依赖浏览器环境的 npm 包也不一定能用。`setData` 传递的是可序列化数据，有同步成本，尽量只更新界面需要的部分。[微信官方类型说明](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.component.d.ts)

支付宝的原生页面使用 AXML、ACSS 和 JavaScript，也有数据绑定及事件机制。思路相近，文件、API、组件细节和平台规则需要分别适配。微信项目不能改几个后缀就当支付宝项目交付。[支付宝文件结构说明](https://alipaymo-miniprogram.alipay.com/docs-alipaymo/miniprogram_alipaymo/mpdev/quick-start_understand-the-mini-program-file-structure)

## 这个案例为什么用原生

先看代码实际用了什么：

| 部分 | 当前实现 |
| --- | --- |
| 页面和逻辑 | 微信原生 WXML、JavaScript，使用 `Page`、`Component`、`Behavior` |
| 样式 | Less 和 WXSS，开发者工具启用 Less 编译 |
| UI 依赖 | `tdesign-miniprogram`，当前全局注册了它的图标组件 |
| 业务状态 | `utils/ecosystem.js` 集中处理，本地缓存保存演示数据 |
| 工程检查 | ESLint、Prettier、Node.js 内置测试运行器 |

结合当前范围，我认为原生比较合适：先做微信端，页面规模有限，导航、分享和生命周期都能直接对照微信文档。选型不必一次解决所有未来需求。

如果确定要同时做微信、支付宝和 H5，再评估 uni-app、Taro 这类跨端方案。能复用多少代码，要看组件和平台能力的差异；登录、支付和真机验收仍需逐端完成。

## 工具准备好，先跑通一条流程

日常写代码用熟悉的编辑器即可。另外准备 Node.js、Git、[微信开发者工具](https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html)，以及能扫码测试的手机。支付宝端使用对应的开发者工具和客户端。

这个案例使用 npm 和 `package-lock.json`，先安装依赖：

```sh
npm ci
```

接着在微信开发者工具中导入项目，选择正确的 AppID，执行“工具 → 构建 npm”，再普通编译。模拟器里能看到页面后，用预览二维码在手机上打开一次。

这里没有 Web 项目常见的 `npm run dev`：依赖由 npm 安装，小程序的编译、调试、预览和上传由开发者工具完成。项目另外提供两个检查命令：

```sh
npm test       # 业务和页面行为测试
npm run lint   # 代码检查
```

开发时，先跑通“打开页面 → 读取数据 → 跳转 → 返回后刷新”，再扩展其他流程。

登录也要尽早联调。典型微信登录流程是：客户端通过 `wx.login` 获取临时 code，交给业务后端；后端向微信换取身份信息，再签发自己的登录凭证，AppSecret 留在服务端。微信身份如何关联已有业务账户，需要双方约定；登录本身也不等于拿到了手机号。[微信登录说明](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)

接接口时，按平台要求配置请求、上传和下载域名。开发工具里关闭域名校验只能帮助调试，验收时要恢复校验，用实际环境验证。[微信网络说明](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)

## 架构不用复杂，边界要清楚

跑通页面后，业务逻辑很容易越写越多。这个项目把共享逻辑和状态处理从页面中提了出来：

```text
pages/                       页面展示、输入、跳转
components/                  导航等公共组件
behaviors/ecosystem-page.js  账户刷新、登录引导、Tab 同步
utils/ecosystem.js           状态转换、展示数据、本地缓存
tests/                       业务规则和页面行为测试
```

页面调用 `dispatch(action)`，状态模块用 `reduce(state, action)` 计算下一份状态，再由 `viewState()` 整理展示数据。于是“兑换码重复提交会不会重复入账”可以脱离界面测试。

路由上，首页、卡册和“我的”放在主包，账户页和登录页放在分包。账户页通过 `screen` 参数承载明细、兑换、结果等子界面，减少了原型阶段的页面文件数量。代价也很直接：分支集中到一个页面，继续扩展时应按独立流程拆分。

分包让非首页流程按需加载，但公共依赖和静态资源放在哪里，仍会影响首包大小，要用开发者工具的包体分析确认。

接入后端时，要保留清楚的数据边界：**前端提交操作、展示状态，服务端确认真实余额、兑换结果和卡片归属，并负责鉴权和防止重复执行。** 当前的本地状态模块适合验证交互规则，正式业务还需要接口层和异常处理。

## 测试时，多想几种“没走完”

我会分三层验证：

1. **业务测试。** 重复兑换、非法金额、转赠锁定、结果未知后的恢复、切换账户后的数据隔离。案例已有相应自动化测试；接入后端后，还要验证真实接口下的结果。
2. **开发者工具。** 检查页面跳转、返回栈、空状态、错误提示、分包加载和控制台报错。
3. **真机与体验版。** 至少覆盖实际目标中的 iOS、Android，重点看安全区、键盘遮挡、滚动、原生分享、弱网和授权拒绝。

账户类应用尤其要测半途离开：提交兑换后切到聊天，过一会再回来；服务端可能已经完成，但客户端没有收到结果。这时应查询并恢复状态，不能简单提示“失败，请重试”。

返回已有页面不一定重新触发 `onLoad`，需要刷新的数据通常在 `onShow` 获取。案例就在这里刷新账户、恢复操作，并在 `onUnload` 清理定时器。还要考虑页面隐藏时哪些任务应暂停，避免后台任务继续运行。

## 上线前，分清备案和版本审核

先分清两个容易混在一起的流程：

- **小程序备案**：在中国大陆提供互联网信息服务，小程序也纳入 APP 备案范围。主办者通过平台提交主体、负责人和业务等资料，由平台查验并报通信管理局审核；应在开展业务前完成，已有网站备案也不能直接代替小程序备案。
- **版本审核**：微信、支付宝等平台对提交版本的功能、内容、类目和隐私等进行审核。备案通过不等于版本审核通过，更新版本仍需按平台流程提审。

备案可以与开发并行。工信部说明的时限是：管局收到齐全、准确的材料后，在 **20 个工作日内**予以备案。平台查验、补材料和版本审核的时间还需另算，不能理解成“从注册到上线最多 20 天”。[工信部备案解读](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)、[小程序适用范围说明](https://ynca.miit.gov.cn/zwgk/tzgg/art/2024/art_9a052419399c4efbbd43b87172e658b8.html)

小程序前端通常走：

**上传代码 → 体验版验收 → 提交版本审核 → 审核通过 → 发布。**

提审前准备好基础信息、类目、隐私说明，以及审核所需的测试账号或操作路径；发布前确认备案等上线条件已满足。具体要求以平台后台为准。[微信发布指引](https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/release.html)

后端需要单独部署。提审版本应连接可供审核验证、并与上线安排一致的环境，不能依赖开发者电脑上的服务。

用户手机里可能仍在运行旧代码，接口升级要保留兼容窗口。案例接入了 `wx.getUpdateManager()`，在新版本准备好后询问用户是否重启，但更新提示不能保证所有人立刻升级。

第一次可以手动走完整个流程，稳定后再用官方 [miniprogram-ci](https://github.com/wechat-miniprogram/miniprogram-ci-dist) 自动化预览和上传。

## 到底要多久

如果已有明确设计、可用接口和平台账号，一个熟悉 Web 的开发者，可以按下面的量级做**初步估算**；这不是本项目的实测工时：

| 工作 | 初步预留 |
| --- | --- |
| 熟悉工具，跑通首条流程 | 1～2 个工作日 |
| 几个简单页面组成的可交互演示 | 3～5 个工作日 |
| 小型业务第一版的前端开发、联调和真机修复 | 2～4 周 |

表中时间有重叠，不应直接相加，也不包含后端开发、资质准备、备案和审核等待。像本案例这样涉及充值、兑换和转赠，还应按具体业务重新估算。

## Web 经验能用上，但交付习惯要调整

组件拆分、状态管理、接口设计和 CSS 基础，都能继续用。需要重新适应的，主要是平台 API、页面生命周期，以及开发者工具和真机之间的差异。

普通 Web 页面通常由团队控制部署节奏，小程序还要经过平台审核，并考虑客户端更新。这会让“代码写完”和“用户能用”之间多出一段工作。最好第一天就扫码跑真机，开发期间持续验证，而不是最后才交给手机测试。

所以第一次接到需求，我会先争取一个明确的阶段目标：**账号能用，真机能跑，一条真实业务流程走通。** 到这一步，再估剩下的工作，才比较有底。
