假设某天工作群里多了一条消息：“这个功能再做个微信小程序吧，应该跟网页差不多。”

如果之前一直写 Web，第一反应多半是：用 Vue 还是 React？页面能不能直接搬？开发者工具又是什么？

先别急着建项目。第一次做小程序，页面通常不是最难的部分。账号权限、登录方式、真机差异和发布审核，才是排期里容易漏掉的工作。

下面拿 `exai-miniprogram` 做案例。它是一个账户类小程序，包含钱包、卡册、兑换、转赠和资料编辑。**当前代码是可交互的前端演示，正式登录、验证码、支付和资产归属仍待后端接入**。我们借它讨论怎么起步，不把演示效果当成已经上线的业务。

## 第一天，先把“能不能做”问清楚

我会先确认四件事：

- **做给谁，第一版做到哪里？** 先列出必须走通的用户流程，例如登录、查看账户、兑换、查看结果。别用“十个页面”代替需求边界。
- **谁提供平台账号？** 小程序归哪个主体，AppID 是否已有，谁是管理员，开发者和体验者权限由谁添加。
- **需要哪些平台能力？** 登录、手机号、分享、支付分别核对；主体、服务类目、资质、备案和隐私声明等准备工作，按实际业务及平台后台要求确认。
- **后端准备到哪了？** 有没有测试环境、HTTPS 域名、接口契约，以及账户和订单的负责人。

这些事情可以和页面开发并行，但不能等到“准备上线”才开始。尤其是充值、兑换这类功能，要先确认业务能否按预期提供，再讨论按钮怎么画。

## 小程序，究竟运行在哪里

网页由浏览器打开 URL，加载 HTML、CSS 和 JavaScript。小程序则把代码和资源组织成平台识别的包，由微信、支付宝这样的**宿主 App**加载和运行；业务数据仍可以请求自己的服务器。

宿主提供页面管理、组件和设备能力，开发者通过平台 API 调用。例如微信用 `wx.request` 发请求、`wx.navigateTo` 打开页面，支付宝则有自己的 `my.*` API。

以微信原生框架为例，视图层负责显示，逻辑层负责处理事件和数据。点按钮后，事件交给逻辑层；逻辑处理完，通过 `setData` 把需要展示的数据同步回去。可以把它记成：

**点按钮 → 执行业务逻辑 → 更新视图数据 → 界面变化。**

这也意味着，不要照搬 `document.querySelector` 或直接操作 DOM 的习惯；依赖浏览器环境的 npm 包也不能默认可用。`setData` 传递的是可序列化数据，尽量只更新界面需要的部分。[微信官方类型说明](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.component.d.ts)

支付宝的原生页面使用 AXML、ACSS 和 JavaScript，也有数据绑定及事件机制。思路相近，文件、API、组件细节和平台规则需要分别适配。微信项目不能改几个后缀就当支付宝项目交付。[支付宝文件结构说明](https://alipaymo-miniprogram.alipay.com/docs-alipaymo/miniprogram_alipaymo/mpdev/quick-start_understand-the-mini-program-file-structure)

## 这个案例为什么用原生

先看代码实际用了什么：

| 部分 | 当前实现 |
| --- | --- |
| 页面和逻辑 | 微信原生 WXML、JavaScript，使用 `Page`、`Component`、`Behavior` |
| 样式 | Less 和 WXSS，开发者工具启用 Less 编译 |
| UI 依赖 | `tdesign-miniprogram`，当前全局注册了它的图标组件 |
| 业务状态 | `utils/ecosystem.js` 集中处理，本地缓存保存演示数据 |
| 工程检查 | ESLint、Prettier、Node.js 内置测试运行器 |

从这个项目的范围看，原生是一个容易解释的选择：先交付微信端，页面规模有限，又要接触微信自己的导航、分享和生命周期。少一层框架转换，查文档、定位问题都更直接。这是对现有选型的分析，并非项目已经验证过所有方案。

如果需求一开始就是微信、支付宝和 H5 同步交付，再评估 uni-app、Taro 这类跨端方案更合适。熟悉 Vue 或 React 能减少学习成本，但平台登录、支付和真机验收，仍然要分别完成。

## 架构不用复杂，边界要清楚

这个项目值得借鉴的是业务逻辑没有全部塞进页面事件：

```text
pages/                       页面展示、输入、跳转
components/                  导航等公共组件
behaviors/ecosystem-page.js  账户刷新、登录引导、Tab 同步
utils/ecosystem.js           状态转换、展示数据、本地缓存
tests/                       业务规则和页面行为测试
```

页面调用 `dispatch(action)`，状态模块用 `reduce(state, action)` 计算下一份状态，再由 `viewState()` 整理展示数据。于是“兑换码重复提交会不会重复入账”可以脱离界面测试。

路由上，首页、卡册和“我的”放在主包，账户页和登录页放在分包。账户页通过 `screen` 参数承载明细、兑换、结果等子界面，减少了原型阶段的页面文件数量。代价也很直接：分支集中到一个页面，继续扩展时应按独立流程拆分。

分包也不是把目录挪走就结束了。业务状态模块被首页引用，仍需随首页加载；首包实际带了什么，要看开发者工具里的代码依赖和包体分析。

更需要守住的是数据边界：**本地缓存适合保存演示和展示状态，真实余额、兑换结果、卡片归属必须由服务端确认。** 接入后端后，前端负责提交操作、展示处理中状态、查询最终结果，服务端负责鉴权和防止重复执行。

现有 `api/request.js` 也不能原样当成可靠的接口层：它用 `res.code` 判断 HTTP 成功，接入时应区分 `res.statusCode` 与 `res.data` 中约定的业务状态。目录里有请求封装，不代表联调已经完成。

## 工具准备好，先跑通一条流程

日常写代码用熟悉的编辑器即可；另外准备 Node.js、Git、微信开发者工具，以及能扫码测试的手机。支付宝端使用对应的开发者工具和客户端。

这个案例使用 npm 和 `package-lock.json`，启动步骤是：

```sh
npm ci
npm test
npm run lint
```

接着在微信开发者工具中导入项目，选择正确的 AppID，执行“工具 → 构建 npm”，再普通编译。这里没有 Web 项目常见的 `npm run dev`：依赖安装交给 npm，小程序编译、模拟器、预览和上传由开发者工具承担。

开始开发时，先跑通“一个页面 → 一次数据读取 → 一次跳转 → 返回后刷新”。确认这条链路成立，再铺其他页面。

登录也要尽早联调。典型微信登录流程是：客户端通过 `wx.login` 获取临时 code，交给业务后端；后端向微信换取身份信息，再签发自己的登录凭证。AppSecret 留在服务端。当前案例的登录是模拟流程，不能用它代替这一步。[微信登录说明](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)

接真实接口时，按平台要求配置请求、上传和下载域名。开发工具里关闭域名校验只能帮助本地调试，验收时应恢复校验，使用正式配置。[微信网络说明](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)

## 测试时，多想几种“没走完”

我会分三层验证：

1. **业务测试。** 重复兑换、非法金额、转赠锁定、结果未知后的恢复、切换账户后的数据隔离。案例已经有这些方向的自动化测试，但本地状态测试不能证明服务端交易安全。
2. **开发者工具。** 检查页面跳转、返回栈、空状态、错误提示、分包加载和控制台报错。
3. **真机与体验版。** 至少覆盖实际目标中的 iOS、Android，重点看安全区、键盘遮挡、滚动、原生分享、弱网和授权拒绝。

账户类应用尤其要测半途离开：提交兑换后切到聊天，过一会再回来；服务端可能已经完成，但客户端没有收到结果。这时应查询并恢复状态，不能简单提示“失败，请重试”。

生命周期也和写网页时的直觉有差别。返回已有页面不一定重新触发 `onLoad`，需要刷新的数据通常放在 `onShow`；页面隐藏和销毁也要分别考虑。案例在 `onShow` 刷新账户、恢复操作，在 `onUnload` 清理结算定时器。接真实接口后，还要处理旧请求晚返回覆盖新页面数据的问题。

## 上线，要走两条发布流程

先分清两个容易混在一起的流程：

- **小程序备案**：在中国大陆提供互联网信息服务，小程序也纳入 APP 备案范围。主办者通过平台提交主体、负责人和业务等资料，由平台查验并报通信管理局审核；应在开展业务前完成，已有网站备案也不能直接代替小程序备案。
- **版本审核**：微信、支付宝等平台对提交版本的功能、内容、类目和隐私等进行审核。备案通过不等于版本审核通过，更新版本仍需按平台流程提审。

因此，备案要在项目早期启动，可以与开发并行。工信部说明的办理时限是：通信管理局收到齐全、准确的材料后，在 **20 个工作日内**予以备案；这不是从开始填表到上线的总耗时承诺，平台查验、补材料和版本审核还需另留时间。[工信部备案解读](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)、[小程序适用范围说明](https://ynca.miit.gov.cn/zwgk/tzgg/art/2024/art_9a052419399c4efbbd43b87172e658b8.html)

小程序前端通常走：

**开发者工具上传 → 设置体验版验收 → 提交版本审核 → 审核通过，确认备案等上线条件已满足 → 发布。**

提审前准备好平台要求的基础信息、类目、隐私说明，以及审核所需的测试账号或操作路径。具体材料和审核进度以平台后台为准，排期不要建立在“提交当天一定能通过”上。[微信发布指引](https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/release.html)

业务后端则单独部署到自己的基础设施或云服务。上传小程序不会顺便发布接口，测试环境地址也不会自动变成生产地址。

还有一个 Web 开发者容易忽略的区别：用户手机里可能仍在运行旧代码。前后端发布要保留兼容窗口，不能一更新接口就让旧客户端失效。案例已经接入 `wx.getUpdateManager()`，新版本准备好后询问用户是否重启，但更新提示不能替代接口兼容。

第一次可以手动走完整个流程，稳定后再用官方 [miniprogram-ci](https://github.com/wechat-miniprogram/miniprogram-ci-dist) 自动化预览和上传。当前仓库的 PR 工作流只运行 lint，还没有自动发布小程序。

## 到底要多久，和 Web 有什么不同

如果已有明确设计、可用接口和平台账号，一个熟悉 Web 的开发者，可以按下面的量级做**初步估算**；这不是本项目的实测工时：

| 工作 | 初步预留 |
| --- | --- |
| 熟悉工具，跑通首条流程 | 1～2 个工作日 |
| 几个简单页面组成的可交互演示 | 3～5 个工作日 |
| 小型业务第一版的前端开发、联调和真机修复 | 2～4 周 |

这些范围有重叠，不应直接相加。账户、支付、复杂授权会增加联调成本；账号、资质、备案、后端开发和平台审核要单独确认。像本案例这样含充值、兑换、转赠的需求，不能拿原型完成速度承诺正式上线时间。

写起来，样式、组件拆分和状态管理都很熟悉。不同的感觉主要来自交付方式：网页改完部署就能打开，小程序多了宿主能力、平台权限、体验成员和审核流程；浏览器调试很方便，小程序却更早要求我们拿起手机。

所以第一次接到需求，我会先争取一个明确的阶段目标：**账号能用，真机能跑，一条真实业务流程走通。** 到这一步，再估剩下的工作，才比较有底。
